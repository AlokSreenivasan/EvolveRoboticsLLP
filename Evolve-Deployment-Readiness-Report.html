Executive summary

Evolve is a feature-complete robotics/learning app: courses and YouTube playlists, assignments, exams, quiz competitions, projects, events, push notifications, streak/XP gamification, a keyword chatbot, and a full in-app CMS across ~301 TypeScript files and 46 screens. The architecture has genuinely good bones — server-authoritative exam/quiz scoring via Cloud Functions, answer keys isolated in admin-only collections, and a 773-line Firestore ruleset with role helpers and audience targeting.

However, the app cannot be shipped in its current state. The admin authorization model is contradictory (UI restrictions are not enforced by rules, and two callable Functions reject superadmins outright, making Notifications and Manage Users features effectively broken). Account deletion violates its own promise to users by orphaning six Firestore subcollections. The codebase fails its own quality gates — TypeScript does not compile, ESLint reports 24 errors, and one Jest suite is broken. There is no CI/CD, no staging environment, no crash reporting, no App Check, and the iOS project still carries the React Native example bundle identifier, which the App Store will not accept.

Every issue below includes a concrete fix. The blocking set is estimated at 1–2 focused weeks; hardening (Phase 1) at a further 2–3 weeks.

1. Release blockers (fix before any store build)

BlockerSEC-01Admin UI restrictions are not enforced by Firestore/Storage rules

The UI restricts plain admin users to four screens (ManageResources, ManageAssignments, ManageExams, ManageQuizCompetitions) via adminDashboardAccess.ts and AdminFeatureRouteGuard.tsx. But the Firestore isAdmin() helper treats admin and superadmin identically for nearly every CMS collection. Any plain admin can bypass the UI with a direct Firebase SDK call and mutate courses, notifications, projects, schools, playlists, and more. UI guards are never an authorization boundary.

Evidence: src/utils/admin/adminDashboardAccess.ts · firestore.rules lines 176–197 (isAdmin/isSuperAdmin)

Fix

Mirror the UI permission matrix in the rules. Keep isSuperAdmin() for full CMS access and restrict isAdmin() to the four content types plain admins may manage:

// firestore.rules — replace broad isAdmin() usage per-collection
function isContentAdmin(database) {          // admin OR superadmin
  return isAdmin(database);
}
// Collections plain admins may write:
match /resources/{id}       { allow write: if isContentAdmin(database); }
match /assignments/{id}     { allow write: if isContentAdmin(database); }
match /exams/{id}           { allow write: if isContentAdmin(database); }
match /quizCompetitions/{id}{ allow write: if isContentAdmin(database); }
// Everything else in the CMS: superadmin only
match /courses/{id}         { allow write: if isSuperAdmin(database); }
match /notifications/{id}   { allow write: if isSuperAdmin(database); }
match /projects/{id}        { allow write: if isSuperAdmin(database); }
match /schools/{id}         { allow write: if isSuperAdmin(database); }

Apply the same split in storage.rules for image/PDF upload paths. Add Firestore rules unit tests (see QG-03) asserting a plain admin cannot write to courses.

BlockerSEC-02Superadmins are rejected by admin-only Cloud Functions — two features broken

sendLiveNotification (line 279) and resetUserQuizProgress (line 397) check role !== 'admin' exactly. The screens that call them (Admin Notifications, Manage Users) are superadmin-only in the UI. Result: superadmins open the screens but every server call fails with permission-denied; plain admins would pass the server check but cannot reach the screens. Both features are unusable through any supported path. Ironically the file already contains the correct helper — isAdminRole() (line 438) accepts both roles but is only used by migrateAnswerKeys.

Evidence: functions/index.js:279, 397, 438 · src/presentation/screens/Admin/Notifications.tsx · ManageUsers.tsx

Fix
// functions/index.js — hoist isAdminRole above the callables and use it
// (decide per-function whether plain admins should also qualify;
//  for superadmin-only features, add:)
function isSuperAdminRole(role) { return role === 'superadmin'; }

// sendLiveNotification (matches the superadmin-only UI):
if (!adminSnap.exists || !isSuperAdminRole(adminSnap.data().role)) {
  throw new HttpsError('permission-denied', 'Only superadmins can send live notifications.');
}
// resetUserQuizProgress: same replacement.

Then redeploy: firebase deploy --only functions. Add a Functions unit test that calls each callable as admin, superadmin, and user and asserts the expected allow/deny.

BlockerPRI-01Account deletion orphans six Firestore subcollections

deleteAccountService.ts deletes the users/{uid} document, profile images, and the Auth account — but Firestore never cascades deletes. These subcollections survive forever: continueLearningProgress, examAttempts, quizAttempts, fcmTokens, notificationPreferences, notificationReads. The UI tells users their associated data is removed; that claim is currently false. This is a GDPR/DPDP right-to-erasure exposure and also leaves live FCM tokens that can still receive pushes.

Evidence: src/services/firebase/deleteAccountService.ts (deletes only the parent doc)

Fix

Move deletion server-side where the Admin SDK can delete recursively. Two robust options:

// Option A (recommended): Auth-triggered cleanup — also covers console deletions
const functions = require('firebase-functions/v1');
exports.onUserDeleted = functions.auth.user().onDelete(async (user) => {
  const db = getFirestore();
  await db.recursiveDelete(db.doc(`users/${user.uid}`)); // removes all subcollections
});

// Option B: callable invoked before authUser.delete() in deleteAccountService.ts
exports.deleteMyAccountData = onCall(async (request) => {
  if (!request.auth) throw new HttpsError('unauthenticated', 'Sign in first.');
  const db = getFirestore();
  await db.recursiveDelete(db.doc(`users/${request.auth.uid}`));
  return { ok: true };
});

Keep the client-side Storage image cleanup, then call the function, then delete the Auth user. Add a test that seeds subcollection docs and asserts none remain after deletion.

BlockerQG-01TypeScript does not compile — 12 errors

npx tsc --noEmit fails. Several errors are real behavior bugs, not annotations:

  • MainStack.tsx:66 — initialState is not a valid prop on Stack.Navigator in React Navigation 7; it is silently ignored, so the "require profile completion" redirect never works via this prop.
  • QuickAccessGrid.tsx:71 — string width not assignable to DimensionValue.
  • ManageContinueLearningPlaylists.tsx:525, 564 — autoCorrect passed to a FormField that doesn't accept it.
  • continueLearningPlaylistsService.ts, fcmTokenService.ts, notificationPreferencesFirestoreService.ts — error codes VALIDATION_ERROR, PUSH_UNREGISTRATION_ERROR, NOTIFICATION_PREFERENCES_SYNC_ERROR missing from the FirebaseServiceErrorCode union; plus an unknown-to-boolean assignment.
  • profilePhotoPicker.ts:97 — 0.85 is not a valid PhotoQuality (must be one of the allowed literals, e.g. 0.8).
  • dailyStreakXp.test.ts:1–2 — import paths off by one directory level.

Evidence: npx tsc --noEmit output, 17 Jul 2026

Fix

Point fixes in order: (1) pass initialState to NavigationContainer or use a conditional initialRouteName/imperative navigation.reset() for the profile-completion redirect; (2) type the width as DimensionValue (e.g. '48%' as DimensionValue or compute a number); (3) add autoCorrect?: boolean to FormFieldProps and forward it to TextInput; (4) extend the FirebaseServiceErrorCode union with the three missing codes and cast the Firestore read before assigning to boolean; (5) change quality to 0.8; (6) fix the two test import paths. Then add "typecheck": "tsc --noEmit" to package.json scripts and gate CI on it.

BlockerQG-02ESLint fails with 24 errors (44 problems) — several are runtime hazards

The react-hooks/exhaustive-deps errors are not cosmetic: Notifications.tsx:293 omits handleSendLiveNotification from a useCallback dependency array (stale closure over send logic); CoursePlaylistScreen.tsx:44 and CourseVideoScreen.tsx:41 compute objects with || expressions that change identity every render, defeating memoization for watch-progress tracking; ExamAttemptScreen.tsx:99 omits exam from a useEffect. Plus unused imports (View, TouchableOpacity, _removed ×2) and 20 warnings.

Evidence: npm run lint output, 17 Jul 2026

Fix

For each hook error: wrap derived objects in useMemo (e.g. const watchSecondsByVideoId = useMemo(() => progress?.byVideo ?? {}, [progress])), add the missing dependencies, and verify the affected flows (send notification, exam timer, resume playback) manually afterwards. Delete unused imports. Decide a policy for the no-void warnings (either allow void promise in .eslintrc with {"allowAsStatement": true} or replace with explicit .catch()). Gate CI on eslint . --max-warnings 0.

BlockerOPS-01No CI/CD — nothing prevents broken code from shipping

There are no GitHub Actions, no Fastlane, no automated checks of any kind. Given that the repo currently fails tsc, ESLint, and Jest simultaneously, this is not hypothetical — unverified code is already on the main branch. Firestore rules and Functions are deployed by hand with no verification step.

Evidence: no .github/workflows, no Fastlane, no pipeline config anywhere in the repo

Fix
# .github/workflows/ci.yml — minimum viable gate
name: CI
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npx tsc --noEmit
      - run: npx eslint . --max-warnings 0
      - run: npm test -- --ci
      - run: cd functions && npm ci && npm run lint --if-present

Phase 2: add an Android release-build job (./gradlew bundleRelease with a debug keystore), Firestore rules tests via the emulator, and Fastlane lanes for store delivery.

BlockerOPS-02iOS release identity is still the React Native example template

The bundle identifier is org.reactjs.native.example.Evolve and no DEVELOPMENT_TEAM is set. Apple rejects example bundle IDs, and the ID is baked into the committed GoogleService-Info.plist and Google Sign-In configuration, so changing it late means re-issuing Firebase iOS app config and OAuth clients. Version is 1.0 (build 1) with no versioning scheme.

Evidence: ios/Evolve.xcodeproj/project.pbxproj:294, 321 · ios/GoogleService-Info.plist

Fix
  1. Register com.evolve (matching Android) in the Apple Developer portal; set PRODUCT_BUNDLE_IDENTIFIER and DEVELOPMENT_TEAM in both Debug/Release configs.
  2. Add a new iOS app with that bundle ID in the Firebase console; replace GoogleService-Info.plist; update the reversed client ID in the URL scheme for Google Sign-In.
  3. Create an iOS OAuth client for the new bundle ID; verify sign-in end to end.
  4. Adopt a version scheme (e.g. marketing 1.0.0, build = CI run number) shared with Android versionCode/versionName.

2. High severity

HighDEP-0124 npm vulnerabilities in the production dependency graph — 6 critical

npm audit --omit=dev (670 prod packages): critical — @react-native-community/cli arbitrary OS command injection, protobufjs code execution ×2, fast-xml-parser entity-expansion DoS/bypass, shell-quote newline escape, websocket-driver ×2; high — @grpc/grpc-js crash vectors, ws memory-exhaustion DoS, minimatch and picomatch ReDoS; plus 13 moderate, 1 low.

Evidence: npm audit --omit=dev --json, 17 Jul 2026

Fix

Run npm audit fix first — the majority (websocket-driver, ws, yaml, and others) resolve within semver ranges. For the rest: the CLI advisories are dev-tooling reachable via transitive prod graph — upgrade @react-native-community/cli to ≥20 alongside the React Native upgrade, or accept with a documented exception since they don't ship in the app binary; protobufjs/grpc-js come via Firebase Admin in functions/ — run npm audit fix there and bump firebase-admin to the latest 13.x. Re-run audit in CI (npm audit --omit=dev --audit-level=high) so regressions fail the build. Do not use npm audit fix --force blindly — it will jump React Native majors.

HighSEC-03No App Check, rate limiting, or abuse controls on callable Functions

Any device with a valid Firebase Auth token can invoke submitExamAttempt, submitQuizAttempt, and the admin callables at unlimited rate from outside the app (the Firebase config in the binary is extractable). There is no App Check attestation, no per-user throttle, and no abuse monitoring — exam submissions can be scripted.

Evidence: functions/index.js — no enforceAppCheck; no App Check SDK in package.json

Fix
// 1. Client: add @react-native-firebase/app-check (Play Integrity / App Attest)
// 2. Functions: enforce attestation
exports.submitExamAttempt = onCall({ enforceAppCheck: true }, async (request) => { ... });
// 3. Simple per-user throttle inside submit callables:
const recent = await db.collection(`users/${uid}/examAttempts`)
  .where('submittedAt', '>', Timestamp.fromMillis(Date.now() - 60_000)).count().get();
if (recent.data().count >= 3) throw new HttpsError('resource-exhausted', 'Too many attempts.');

Roll out in monitor-only mode first, then enforce. Also enable App Check for Firestore and Storage in the Firebase console.

HighPRI-02iOS privacy manifest declares no data collection — the app collects plenty

PrivacyInfo.xcprivacy claims nothing is collected, while the app stores name, email, phone, school, grade, track, profile photos, FCM tokens, learning progress, and exam/quiz answers. App Store privacy labels must match; a mismatch risks rejection or post-launch enforcement. Android's Play Data Safety form will need the same truthful disclosure.

Evidence: ios/Evolve/PrivacyInfo.xcprivacy vs. users/{uid} schema and fcmTokens subcollection

Fix

Rewrite the manifest with NSPrivacyCollectedDataTypes entries for: Name, Email Address, Phone Number, Photos/Videos (profile image), User ID, Device ID (FCM token), Product Interaction (progress/attempts) — each marked linked-to-identity, not used for tracking. Mirror this in App Store Connect privacy labels and the Play Data Safety form. Since this is an education app plausibly used by minors ("kids track"), have counsel review COPPA/GDPR-K obligations before launch. Publish a privacy policy URL (required by both stores) covering the deletion behavior fixed in PRI-01.

HighQG-03Test suite is thin and partially broken; no tests where the risk actually lives

Five Jest suites exist; App.test.tsx fails because Jest can't transform the ESM build of @react-native-firebase/messaging (jest.config.js is only preset: 'react-native' — no transformIgnorePatterns or mocks). Coverage has no collectCoverageFrom or thresholds. There are zero tests for Firestore rules, Storage rules, Cloud Functions, auth flows, or account deletion — precisely the areas where this audit found blockers.

Evidence: jest.config.js · __tests__/App.test.tsx failure · absence of @firebase/rules-unit-testing

Fix
// jest.config.js
module.exports = {
  preset: 'react-native',
  transformIgnorePatterns: [
    'node_modules/(?!(react-native|@react-native|@react-native-firebase|@react-navigation)/)',
  ],
  setupFiles: ['./jest.setup.js'],   // mock @react-native-firebase/* modules here
  collectCoverageFrom: ['src/**/*.{ts,tsx}', '!src/**/__tests__/**'],
};

Then add, in priority order: (1) Firestore rules tests with @firebase/rules-unit-testing + emulator, covering the SEC-01 permission matrix; (2) Functions tests for role checks (SEC-02) and recursive deletion (PRI-01); (3) unit tests for gamification/attempt scoring. E2E (Detox/Maestro) can follow post-launch.

HighOPS-03Single Firebase environment, no crash reporting, no monitoring

One Firebase project serves development and (future) production — rules experiments and test data hit real users. There is no Crashlytics, no analytics, no performance monitoring, and no alerting. Post-launch, crashes and Function failures would be invisible.

Evidence: .firebaserc (single project) · no crash/monitoring SDK in package.json

Fix

(1) Create a separate evolve-staging Firebase project; add project aliases in .firebaserc and use build flavors (Android productFlavors, iOS schemes) to select the matching google-services.json / plist per environment. (2) Add @react-native-firebase/crashlytics and, optionally, perf — one install step given the existing RNFirebase setup. (3) In Google Cloud Monitoring, alert on Function error rate and p95 latency for the submit callables. (4) Deploy rules/Functions to staging first in CI, production on tagged release.

3. Medium severity

MediumARC-01Notification fan-out scans every user and never cleans up dead tokens

sendLiveNotification loads all notification preferences and runs a collectionGroup('fcmTokens') scan of every token in the database per send, then ignores FCM per-token failures — invalid/rotated tokens accumulate forever, inflating both read costs and failure counts. Fine at 100 users; expensive and slow at 10,000.

Evidence: functions/index.js lines 325–367 (loadNotificationPreferencesByUser, collectionGroup('fcmTokens'))

Fix

Short term: inspect sendEachForMulticast responses and delete token docs whose error is messaging/registration-token-not-registered or invalid-argument. Medium term: switch to FCM topics — subscribe devices to school_{id}/category_{name} topics client-side on token registration, and publish to topics instead of enumerating tokens. This removes both full-collection scans entirely.

MediumSEC-04Storage rules accept uploads with missing contentType (fail-open)

storage.rules validates file type with !('contentType' in request.resource) || request.resource.contentType.matches(...) — an upload that omits contentType passes. A crafted client could store arbitrary payloads under image/PDF paths.

Evidence: storage.rules contentType conditions

Fix
// Fail closed — require the header and match it:
allow write: if request.resource.contentType != null
          && request.resource.contentType.matches('image/(jpeg|png|webp)')
          && request.resource.size < 5 * 1024 * 1024;
MediumSEC-05One-time migration function migrateAnswerKeys remains deployed (not in earlier summary)

The callable scans entire exam/quiz collections and rewrites answer-key documents. It is admin-callable (isAdminRole, line 816), has served its purpose, and is a standing full-collection write primitive — pure attack/mistake surface.

Evidence: functions/index.js:816

Fix

Delete the export and redeploy (firebase deploy --only functions removes unlisted functions after confirmation). If migrations may recur, keep the code in a scripts/ folder run locally with a service account, never as a deployed callable.

MediumSEC-06Any authenticated user can read any user's profile image (not in earlier summary)

Storage rules gate profile-image reads on authentication only, not ownership or a legitimate social feature — every signed-in user can enumerate and fetch other users' photos, including minors on the kids track.

Evidence: storage.rules profile-images path (read: authenticated)

Fix

If profile photos are only shown to the owner, restrict reads to request.auth.uid == userId in the path match. If they're shown in shared surfaces (leaderboards), keep authenticated read but document it as intentional in the privacy policy, and ensure image paths are unguessable UIDs (they are — verify no listing rule exists).

MediumPRI-03PII and role cached unencrypted in AsyncStorage

profileCache.ts stores name, email, phone, school, grade, track, and role in plain AsyncStorage for 10 minutes. AsyncStorage is unencrypted (SharedPreferences / plist-adjacent files); on a compromised or shared device this is readable. The cached role also drives UI gating, so a demoted admin keeps admin UI for up to 10 minutes (rules still block server-side).

Evidence: src/services/profileCache.ts

Fix

Move the cache to react-native-keychain or react-native-mmkv with encryption enabled, or reduce cached fields to non-PII (uid, displayName, track). For role freshness, re-read the profile document on app foreground and on admin-screen entry rather than trusting the cache.

MediumPRI-04PDFs leak to Google Docs Viewer; WebView has no origin allowlist

pdfViewerUrl.ts wraps Firebase Storage download URLs (which embed access tokens) in docs.google.com/viewer?url=..., disclosing tokenized URLs to a third party. ResourcePdfViewerScreen.tsx sets no originWhitelist or navigation interception, and content URLs are admin-controlled.

Evidence: src/utils/resources/pdfViewerUrl.ts · ResourcePdfViewerScreen.tsx

Fix

Render PDFs natively with react-native-pdf (or react-native-blob-util download + native viewer), removing the third-party hop entirely. If the WebView stays for other content, add originWhitelist={['https://firebasestorage.googleapis.com']} and an onShouldStartLoadWithRequest handler rejecting other hosts.

MediumOPS-04Build hygiene: dual lockfiles, floating native dependency, minification off

Both package-lock.json and yarn.lock are committed — two installers produce different graphs. Android depends on androidx.activity:activity:1.9.+ (a floating version that changes under you at build time) and release minification/shrinking is disabled, shipping a larger, unobfuscated APK.

Evidence: repo root lockfiles · android/app/build.gradle (1.9.+, minifyEnabled false)

Fix

Pick npm (CI example above uses npm ci), delete yarn.lock, and add it to .gitignore. Pin androidx.activity:activity:1.9.3. Enable minifyEnabled true + shrinkResources true for release with RNFirebase/Reanimated Proguard keep rules, and verify a release build on-device before shipping.

MediumDOC-01Documentation is boilerplate; About screen unfinished

README.md is the stock React Native template plus brief auth notes. Missing: Firebase project setup, role model and first-superadmin provisioning, rules/Functions deployment, signing, YouTube key restrictions, staging/prod, data-retention behavior, rollback. AboutScreen.tsx renders only the word "About" — a visible-to-users unfinished screen.

Evidence: README.md · src/presentation/screens/About/AboutScreen.tsx

Fix

Write a real README (setup, environments, deploy commands, role bootstrap via a documented one-time script) plus a short OPERATIONS.md (release checklist, rollback, incident contacts). Either finish the About screen (version, licenses, privacy policy link — App Store reviewers look here) or remove it from navigation until done.

MediumARC-03Committed generated iOS artifacts (ios/.tmp/) (promoted from low)

Generated React Native codegen output is committed under ios/.tmp/. Stale generated code can silently diverge from the installed RN version and confuse Xcode builds after upgrades.

Evidence: ios/.tmp/ in version control

Fix

git rm -r --cached ios/.tmp, add ios/.tmp/ to .gitignore, and rely on pod install/codegen to regenerate.

LowMISC-05Committed Firebase client config — verify key restrictions (not in earlier summary)
